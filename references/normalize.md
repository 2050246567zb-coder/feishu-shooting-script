# 原文整理与中间数据

## 选择脚本部分

阅读全文，识别真正的分镜表或脚本正文。账号介绍、档期、品牌话题、报价、通用风格参考链接等不自动变成镜头行。用户说“只放脚本”时，仍保留品牌植入部分的镜头，它们也是脚本。

已有“镜号／画面描述／口播”表格时，一条源镜头对应一行。不要把“所以”“甚至……”等单独镜头吞掉，也不要因为一条口播有多个标点就拆乱已明确的镜头关系。多句话与多个独立画面一一对应时，可拆为相邻行；如果对应关系无法确定，保留原文并只询问影响匹配的关键问题。

只有口播而没有画面描述时，画面描述留空；除非用户要求创作镜头，否则不要补写想象的画面。无口播的空镜可以只填画面描述，两者不能同时为空。

纯正文可按明确分段、句子与场景说明整理，标点和引号仍留在原句中。不要为机械分句删掉原文、改写词句或改变句序。没有镜号就从001开始；数字镜号使用至少三位补零，确保文本排序与脚本顺序一致，原有A/B等后缀可以保留。

## 地点与参考

- 只有原文明确给出场地、场景标题覆盖本段，或用户指定时，才填具体地点。不要把“屏幕特写”推断为“办公室”。
- 多个地点共用一条源镜头时可用“多地点”标签，原有画面描述保留具体地点；不要擅自拆掉用户已确定的镜头。
- 非待定地点在中间 JSON 的 `location_basis` 中保留原文依据或用户指定依据，供检查；这个字段不进入飞书列。
- 图片必须能定位到对应镜头。内嵌图片来自明确的镜头单元格时可直接对应；封面、Logo、通用风格图不要重复贴到所有镜头。
- 没有图则附件留空。不要把“上传参考图”写成一张假附件，不生成图片，不自动访问带凭证的参考链接。

## 原文其他列

默认不导入字幕、花字、原文批注和预计时长这四个独立字段。确实影响拍摄执行的道具或动作要求可以放入拍摄备注；不要把四列内容机械地全部搬进备注。原文合并单元格里的整段时长不能按每个镜头重复计时。保留提取结果供回查，用户要求恢复这些字段时再处理。

## Word 提取

```bash
python <skill-dir>/scripts/extract_docx.py input.docx --output-dir work/<任务>/source
```

输出 `extracted.json`、便于通读的 `extracted.txt`，以及 `media/` 图片。`merged_from` 指明合并起点；不要仅因相邻单元格为空就沿用上一行内容。Word 修订中的删除文本不作为现行台词；插入文本会保留。出现嵌套表格、浮动文本框或无法辨认的结构时，用实际可用的文档工具补充检查，不能宣称提取器覆盖了所有 Word 排版形态。

## normalized.json

由 Codex 理解原文后写出下面的结构。只执行代码层面的类型、数量、文件和去重检查，不由代码猜语义。

```json
{
  "title": "桌面装置拍摄协作脚本",
  "expected_shots": 2,
  "source_files": ["source.docx"],
  "shots": [
    {
      "id": "001",
      "dialogue": "我做了一个桌面装置。",
      "description": "在工作室将装置放到桌面，切到屏幕特写。",
      "location": "工作室",
      "location_basis": "画面描述写明在工作室",
      "notes": "",
      "reference_files": ["source/media/example.png"],
      "source_refs": ["table:1 row:1"]
    },
    {
      "id": "002",
      "dialogue": "碰一下，它就有反应。",
      "description": "手指触碰装置，连续拍清完整动作。",
      "location": "待定",
      "notes": "留出动作结束后的反应时间。",
      "reference_files": [],
      "source_refs": ["table:1 row:2"]
    }
  ]
}
```

相对文件路径以这个 JSON 所在目录为基准，文件必须实际存在。`source_refs`、`location_basis`、`source_files` 仅用于本地追溯，不创建额外的飞书列。不要把私人脚本和任务状态打包进可分发 Skill。
